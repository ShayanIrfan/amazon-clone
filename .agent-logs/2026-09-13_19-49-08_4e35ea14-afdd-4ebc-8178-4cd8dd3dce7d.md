It works because of Vercel's routing rules. One deployment can hold both static files and serverless functions, and `scripts/build-vercel.mjs` writes a routing table that decides, per request, which one answers.

**1. The build creates both halves in one output folder (`.vercel/output`):**
```
.vercel/output/
├── static/               ← the Vite build (client/dist): index.html, assets/*.js, *.css
├── functions/
│   └── api.func/         ← the Express server, bundled by esbuild into index.mjs
│       └── .vc-config.json   (runtime: nodejs22.x, handler: index.mjs)
└── config.json           ← the routing table
```

**2. `config.json` routes each request (rules are checked top to bottom):**
```json
[
  { "src": "^/api(?:/.*)?$", "dest": "/api" },
  { "src": "^/assets/(.*)$", "headers": { "cache-control": "public, max-age=31536000, immutable" }, "continue": true },
  { "handle": "filesystem" },
  { "src": "^/(.*)$", "dest": "/index.html" }
]
```
- **`/api/...`** goes to the Express function. For example, `/api/products?q=phone` reaches the function, and Express matches `/api/products` as it does locally.
- **`/assets/...`** gets a long cache header, then falls through to the next rules.
- **`filesystem`**: if the path is a real file in `static/`, such as `/assets/index-abc.js` or `/favicon.svg`, Vercel serves it.
- **Anything else**, like `/product/123` or `/orders`, gets `index.html`. React Router then renders the right page in the browser, which is why direct inner-page links work.

**3. The function reuses your Express app.** `server/src/vercel.ts` builds the same app with `createApp()` and hands each request to it. It doesn't call `app.listen()`, because Vercel provides the incoming request.
```ts
const app = createApp();
export default async function handler(req, res) {
  await connectDB();   // cached, so warm requests reuse the Atlas connection
  app(req, res);
}
```

**4. The frontend needed no changes.** It always called relative paths like `fetch("/api/cart")`. Locally, Vite's dev proxy forwards `/api` to Express on port 4000. On Vercel, the first routing rule does the same job, so identical frontend code works in both places.

Sharing one domain also avoids three problems:
- **CORS:** the browser sees same-origin requests, so there's nothing to configure.
- **Cookies:** the login and CSRF cookies belong to the same domain, so browsers don't block them as third-party cookies.
- **CSRF check:** it passes because the request's `Origin` matches the host. That's why I added the same-origin rule to `csrf.ts`.

**The Stripe webhook** hits the same URL too: `https://amazon-clone-amber-six.vercel.app/api/payments/webhook` matches the `/api` rule. The function is configured with `shouldAddHelpers: false` so Vercel doesn't parse the request body first; Stripe's signature check needs the raw body.
